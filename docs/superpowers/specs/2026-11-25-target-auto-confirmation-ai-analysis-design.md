# 每日目标自动确认、历史补记与 AI 饮食分析设计

日期：2026-11-25
状态：已确认设计，待书面复核

## 背景与目标

当前手动阶段目标会自动保存，但自动计算目标仍以建议形式存在，必须由用户在首页确认后才进入 `DailyTarget` 持久化。未打开应用或未确认的过去日期因此可能缺少目标，影响日记和趋势解读。本次改造将目标处理统一为可重复执行的 reconciliation，并新增由用户主动触发的纯文本 AI 饮食分析。

目标：

1. 今日目标按照默认阶段方案自动生成并立即生效，用户仍可对当天进行单日修改。
2. 过去有生效阶段但没有目标的日期自动补记，不覆盖任何已有目标。
3. 用户可主动选择近 7、14 或 30 天的已确认饮食记录进行 AI 分析，结果以易读纯文本返回，不使用 JSON 结构化响应。

非目标：

- 不新增后台服务、公共 API Key 或第三方中转。
- 不接入系统级定时任务或后台唤醒。
- 不上传饮食图片、草稿或分析失败的餐食。
- 不持久化 AI 分析报告，不新增报告历史列表。
- 不用 AI 重新计算营养摄入；本地营养计算器仍是数值汇总依据。

## 方案选择

采用统一服务方案：`DailyTargetService` 负责今日目标与历史目标的幂等 reconciliation；AI 分析由独立领域服务和页面负责，复用现有 `LLMClientProviding`、供应商配置与 Keychain。

不采用在多个视图中分别补目标的方案，以免触发时机分散、重复实现和遗漏。不采用报告持久化及后台调度方案，以控制本次改造范围和数据隐私边界。

## 一、每日目标自动确认与修改

### 统一 reconciliation

在 `DailyTargetService` 增加面向应用加载的统一入口，输入当前身体档案和基准日期，返回今日已生效的 `TargetResolution` 及必要的补记摘要。`NutritionHomeViewModel.load()` 调用该入口，而不是分别处理今日目标与历史目标。

处理顺序：

1. 读取全部阶段方案，并按开始日期确定可处理的历史范围。
2. 补记昨天及更早的缺失目标。
3. 生成或读取今日目标。
4. 今日目标无论来自手动还是自动阶段策略，都在生成后立即保存，返回结果不再要求用户确认。
5. 重新读取今日摄入与趋势数据，保证首页、日记和趋势使用同一套已保存目标。

`TargetResolution.requiresConfirmation` 保留用于兼容现有领域类型和既有调用，但 reconciliation 新生成并保存的目标必须返回 `false`。现有 `accept` 可保留为兼容入口，不再是正常 UI 流程的必要步骤。

### 默认计算口径

- 每个日期使用当天 `PhasePlan.contains(date)` 命中的阶段方案。
- 手动策略使用该阶段的手动热量与宏量营养目标。
- 自动策略使用当前 `UserProfile`、该日阶段的能量调整与宏量营养规则计算。
- 当前档案不是历史身体数据快照；界面或文档应明确历史自动补记采用当前档案，避免被解释为历史体重还原。
- 某日没有生效阶段时跳过历史补记；今日没有生效阶段时抛出并展示现有 `TargetEngineError.noActivePhase`，不伪造默认目标。
- 自动策略数据不足或计算失败时保留既有错误语义，不以零值或不完整目标替代。

### 今日单日修改

首页将“待确认目标”改为始终可读的“今日目标”摘要，显示热量、蛋白质、碳水和脂肪，并提供“修改”入口。

修改表单：

- 仅修改今日 `DailyTarget`。
- 四项均要求为有限数值；热量必须大于零，蛋白质、碳水和脂肪允许零但不得为负数，与现有 `ManualNutritionTarget.validated()` 一致。
- 保存后设置 `isSingleDayOverride = true`，沿用今日目标的身份与日期，并持久化。
- 单日修改不改变 `PhasePlan`，不影响昨天、明天或其他日期。
- 后续 reconciliation 读取到该目标后直接保留，不根据阶段方案重算。
- 修改成功后刷新今日指标、目标参考与趋势；失败时保留用户输入并显示错误。

## 二、历史目标补记

### 范围

历史范围从所有不晚于基准日期的阶段方案中最早的 `startDate` 所在日开始，到昨天结束。未来阶段不参与。没有可处理阶段时不创建任何历史目标。

逐日处理时：

- 已有目标：直接跳过，无论其来自自动保存、旧版确认还是单日修改。
- 没有目标且存在生效阶段：按上述默认口径生成并保存。
- 没有目标且没有生效阶段：跳过，不视为错误。
- 同一天重复执行：仍只有一条按日期识别的目标，不重复追加或改写。

### 一致性与失败处理

- 补记使用现有 `DailyTargetStoring`，内存与 SwiftData 实现保持相同领域语义。
- 所有日期先检查再保存，已保存目标不可被 reconciliation 覆盖。
- 如果某个缺失日期因身体数据不足或目标规则无效而失败，不删除任何既有目标，也不把失败日期写成空目标。
- 向用户展示可理解的错误；已成功保存的其他日期保持有效。后续应用加载可重试失败日期。
- 不引入新的 SwiftData 实体或字段，避免仅为本功能进行数据库迁移。

## 三、AI 饮食分析

### 页面与主动触发

在现有“今天、日记、趋势、我的”之外新增“AI 分析”导航项，macOS 侧栏与其他平台标签页均接入。

页面包含：

- 近 7／14／30 天分段选择，默认 7 天。
- 数据范围及隐私说明：仅在点击分析后上传文字记录与每日目标，不上传图片。
- “开始分析”按钮；无已确认记录时显示空状态并禁止无效请求。
- 请求期间显示加载状态并防止重复提交。
- 失败时显示现有 LLM 错误语义并允许重试。
- 成功后以可滚动、可选择的文本显示结果，便于复制。

切换天数只更新待分析范围，不自动发起网络请求。离开页面或重复进入不要求持久化旧报告。

### 数据范围与隐私

“近 N 天”按本地日历的滚动日期窗口计算，包含今天，共 N 个自然日。仅选择 `MealEntryStatus.confirmed` 且 `consumedAt` 落入窗口的餐食。

上传内容：

- 日期、餐别、餐食确认时间。
- 用户原文或备注中属于饮食记录的必要文字。
- 已确认食物组成：名称、数量、单位及可用营养快照。
- 本地计算的每日摄入汇总和对应已保存 `DailyTarget`，用于目标对照。
- 数据不完整标记和未知项目，避免把未知营养解释为零。

不上传内容：

- 图片、图片路径或 base64。
- 草稿、失败记录及其他未被用户确认的模型候选。
- API Key 以外的任何认证信息；API Key 仅按现有方式用于请求头，不进入提示词。
- 与分析无关的档案字段。若需要目标背景，只发送每日目标和营养汇总，不发送完整个人档案。

提示词要求模型区分记录事实、估算与建议；记录缺失时明确说明，不推断未记录餐食，不提供疾病诊断或医疗建议。

### 纯文本 LLM 通道

扩展现有 OpenAI 兼容客户端，增加通用文本生成能力，同时保留现有食物识别的严格 JSON 通道。

AI 饮食分析请求：

- 使用同一 `chat/completions` URL、模型、API Key、超时及 HTTP 错误处理。
- 请求体不包含 `response_format`，服务端因此无需返回 JSON。
- 系统提示要求中文、约 600–900 字、短段落和少量要点，优先覆盖总体模式、目标对照、优点、可执行改进及数据局限。
- 响应只读取文本内容，去除首尾空白；不经过 `JSONDecoder` 或食物候选校验。
- 空文本返回现有 `emptyResult` 或等价明确错误，不展示空白成功页。
- 不在客户端机械截断正常结果；长度主要由提示词约束，避免截断句子。

### 领域服务与视图状态

新增饮食分析领域服务，负责日期窗口、记录过滤、本地汇总、请求材料构造与客户端调用。视图模型只维护可选天数、加载、结果和错误状态，不直接拼装 HTTP 请求。

报告仅作为本次页面状态展示，不写入 SwiftData。每次新分析成功后替换旧结果；失败时不清空饮食记录，也不要求用户重新配置已有 LLM 设置。

## 测试与验收

### 自动化测试

目标服务：

1. 自动阶段今日目标首次加载即保存，`requiresConfirmation == false`。
2. 手动阶段行为不回归。
3. 历史缺失日期按当天阶段方案补记，当前档案用于自动计算。
4. 已有目标、旧版已确认目标和单日修改均不被覆盖。
5. 没有阶段的历史日期跳过，未来阶段不参与。
6. 重复 reconciliation 幂等，无重复目标。
7. 数据不足或非法规则有明确错误，既有目标不丢失。
8. 今日修改只影响当天并正确刷新营养评估。

AI 分析：

1. 7／14／30 天窗口包含今天且边界日期正确。
2. 仅已确认记录进入请求材料，草稿和失败记录被排除。
3. 请求材料包含对应目标、每日汇总与数据不完整信息，不包含图片或图片路径。
4. 请求体不含 `response_format`，普通文本可直接返回，空文本与 HTTP 错误正常处理。
5. 无记录不调用模型；加载中防止重复请求；失败可重试。
6. 现有 JSON 食物识别测试全部保持通过。

## 文件边界与并行实施约定

可将实施拆为两个不重叠的工作面：

1. 目标 reconciliation、今日修改、相关测试。
2. AI 文本客户端、领域服务、AI 页面、相关测试。

共享导航接线由主 agent 完成，避免多个子 agent 同时修改 `MainTabView`、`AppRootView` 或应用入口。主 agent 负责代码审查、冲突整合、完整测试、实际构建和 GitHub 同步。
