# 健身饮食 App：开发设计总索引

> 状态：macOS 桌面版迁移设计已批准
> 使用场景：仅供用户本人在自己的 Mac 上使用
> 默认技术方向：SwiftUI + SwiftData，本地优先，自行配置多模态 LLM API

实施进展见 [实施状态](../../../implementation-status.md)。

## 1. 产品目标

建立以下完整闭环：

**记录饮食 → 用户确认识别结果 → 本地计算营养 → 对照健身目标 → 给出建议 → 周期性复盘与调整。**

App 初版重点管理热量、蛋白质、碳水化合物和脂肪。它是健身饮食记录工具，不提供疾病诊断、治疗或极端饮食方案。

## 2. 已确定的全局决策

以下约定适用于所有模块，后续开发不得无故改变：

1. 仅供个人使用，不开发账号、社交、多用户和公共服务后台。
2. 饮食记录、身体数据和目标默认保存在本机，离线时可查看和编辑。
3. 使用原生 SwiftUI 和 SwiftData；最低部署目标为 macOS 14，可在用户当前的 macOS 27 上运行。
4. 用户自行配置兼容文本和图片理解的 LLM API，密钥保存在 Keychain。
5. LLM 负责理解文本、识别图片和生成解释；本地规则引擎负责营养汇总、目标差额和推荐前后数值计算。
6. 模型返回结果必须结构化并经过校验，不得把模型生成的总热量直接写入数据库。
7. 文本和图片识别结果必须由用户确认后才计入正式饮食记录。
8. 食物份量不明确时展示估算范围或可信等级，允许修改，不伪装成精确测量。
9. 切换阶段或调整目标默认只影响未来，不重写历史目标和历史记录。
10. 单日摄入偏差不触发惩罚性节食或自动修改长期目标；调整以建议形式由用户确认。

## 3. 统一单位与术语

- 能量：千卡（kcal）。
- 蛋白质、碳水、脂肪、纤维：克（g）。
- 体重：千克（kg）；身高：厘米（cm）。
- 食物重量：内部统一为克（g），界面可显示份、个、毫升等原始单位。
- **实际热量缺口**：估算总消耗 − 实际摄入。
- **目标差额**：当天目标摄入 − 实际摄入。
- “休息／恢复阶段”是持续一段时间的方案；“休息日目标”是单日方案，两者不可混用。

## 5. 后续使用 LLM 开发的方法

不要要求 LLM 一次性生成整个 App。每次只处理一个模块：

1. 提供本总索引和当前模块文档。
2. 同时提供当前模块依赖的前置文档及已有相关代码。
3. 明确要求“只实现当前模块，不提前实现后续模块，不改变全局决策”。
4. 要求列出修改文件、关键接口、测试及需要人工验证的事项。
5. 模块通过验收后，再进入下一模块；如设计发生变化，先同步修改文档。

可复用的任务提示：

> 请阅读总索引、当前模块及其前置模块。只实现当前模块，复用已有领域模型和计算引擎。LLM 不得代替本地数值计算，识别结果必须经用户确认。完成后运行相关测试，并汇报修改文件、测试结果和未解决问题。

## 6. 初版不做

- 账号体系、云同步、社交和多人共享。
- 公共 API 服务或复杂远程后台。
- 医疗诊断、疾病饮食治疗、自动极端限食。
- 依赖单次照片给出精确重量或精确营养结论。
- 在数据不可靠时补全维生素、矿物质等微量营养素。
- 第一阶段即接入所有健康平台或可穿戴设备。
