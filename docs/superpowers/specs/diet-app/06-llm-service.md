# 06：LLM 服务与结构化输出

## 目标

建立一个可替换供应商的统一多模态接口，支持文本饮食理解和图片食物识别，不让具体 SDK 或提示词渗透到其他模块。

## 配置

- Base URL、模型名称、API Key 和可选供应商类型。
- API Key 存入 Keychain，其他非敏感配置可本地保存。
- 支持连接测试、超时、有限重试和清晰错误信息。
- 初版不内置公共密钥，不经过第三方中转后台。

## 统一输入输出

文本和图片请求最终都转换为领域层的候选结果，至少包含：

```json
{
  "items": [
    {
      "name": "食物名称",
      "brand": null,
      "quantity": 1,
      "unit": "个",
      "estimatedGrams": null,
      "estimatedGramsRange": null,
      "mealTime": null,
      "nutritionBasis": "模型估算或用户提供",
      "assumptions": ["配方、份量或烹饪方式假设"],
      "missingInformation": ["需要用户补充的信息"]
    }
  ],
  "needsClarification": true,
  "clarificationQuestion": "一个具体的问题"
}
```

该结构只是语义要求，实际开发可定义等价 Swift 类型。数值必须经过本地校验，模型输出不是正式记录。
`estimatedGramsRange` 使用包含下限和上限的两个数值表示；无法估计时为 `null`，不得用零表示未知。

## 营养来源策略

优先级建议为：

1. 用户包装标签或手动营养数据。
2. 已接入且可核验的营养来源。
3. 模型基于常见配方的估算。

模型估算必须标明来源和假设。没有可靠数据时可以只返回食物和份量，等待用户补充，而不是强行生成完整营养表。

## 可靠性要求

- 使用结构化输出或严格 JSON 解析，并处理缺字段、类型错误和多余文本。
- 校验数量、单位、营养范围和必填字段。
- 不把模型自报的置信度当作统计上准确的概率；界面使用高／中／低估算质量及原因。
- 超时或失败时保留原始文本、图片和草稿，允许重试或手动记录。
- 日志不得包含 API Key；饮食文本和图片的日志也应最小化。

## 模块验收

- 更换供应商适配器时，文本记录和图片记录模块无需修改。
- 非法 JSON、空结果、网络错误和限流均不会导致崩溃或数据丢失。
- 模型返回的每日总热量不会绕过本地计算器。
- 请求配置和错误状态可在“我的”页面管理。
